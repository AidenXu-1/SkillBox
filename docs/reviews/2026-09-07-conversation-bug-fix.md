# 对话缺陷修复与语义能力边界

## 本轮结果

用户要求修复只读审查发现的三个 bug，并要求保护已调好的 Skill 查找能力。三个问题均先在当前源码复现，再加入正式测试并修复；保留三栏、名称与作者限定、来源核验、推荐条件、网络预算及安装恢复机制。

1. 新需求“有什么 Skill 可以把 PDF 转成 Word 吗？”原先被 `DiscoveryConversation.action` 的问句分支当成解释已有候选，搜索次数为零。现在询问适用 Skill 是否存在时进入查找；同一判断也用于任务范围，避免“可以”触发补充规则后继承旧作者。已知作者、明确名称和当前候选问题分别回测。
2. 原先只在查找结束时查看当前选中的对话，切走再切回会自动处理队列。现在记录切换导致的暂停，搜索结束不会恢复旧补充；发送新消息也不会恢复停止或重启前留下的队列。手动继续仍可执行，新搜索中正常排队仍可合并。
3. 原先条件数组按语义标签删除，但目标原句仅按字面删词。“不联网”会在撤回“离线”后重新被读成条件。现在删除目标中的完整要求表达及其限定词，保护同句其他要求；继续查找和模型上下文均回测。

## 为什么整体体验仍显得机械

以下结论来自当前源码，不假设 Codex 的内部实现。

### 动作选择早于语义理解

`AppModel.submitDiscoverySearch` 先调用本地 `DiscoveryConversation.action`。被归为解释、比较、撤回的消息直接进入另一个分支；只有查找分支才会调用 `planDiscovery`。因此再好的模型也无法纠正已经被入口拦下的新查找。

当前模型规划主要返回目标、条件和查询词，没有统一返回这轮动作。`DiscoveryIntentPlanner.reconcile` 又将目标、必须条件、排除和对象恢复为本地确定值。这些保护曾解决模型改错作者、创造条件和混入相似作品的问题，应保留；但它们同时说明，整体对话理解目前主要由局部规则承担。

### 状态仍混合在自然语言里

目标原句、条件数组、近期消息和旧查询都可能携带同一要求。一次撤回如果只改变其中一处，其余路径就可能重新推导出旧条件。本轮修复了已确认的同义表达遗漏；更广泛的纠正、替换与条件组合仍需要完整行为样例支持。

### Skill 问答工具和资料范围有限

现有解释入口只使用当前推荐候选中最多三份引用，每份正文至多 1,500 字符；缺少候选或依据时返回澄清/摘录。它没有完整覆盖 Skill 概念、产品操作指导、跨候选深入核对等所有领域问题，也不能按问题再读取所需章节。模型被限定在眼前几份截短资料里，回答能力自然受限。放开虚构引用或安装权限不能解决这些问题。

## 后续改进方向，尚未实施

如果要达到可靠的 Skill 领域助手体验，应补充统一的对话理解层：结合用户最新消息、当前任务和所指对象，提出查找、补充、比较、解释、操作指导或必要澄清等有限动作，再由程序校验并执行。保留现有确定性的身份、证据、预算和写入授权保护，不直接删除已调好的保护规则。

条件需要有清晰的来源与生效状态；问答需要有版本化产品说明和按问题读取作者资料的有限工具。验收应使用未写进规则的自然表达及多轮任务，分别测试模型开启、关闭、失败、停止和恢复。先让新理解结果与旧路径并行对照而不执行，确认精确名称、作者与推荐质量没有退步，再逐步替换动作选择。

本轮没有实现这项整体改造，也没有增加额外模型请求。自动化模型测试使用受控返回值，原生 QA 使用模拟来源；它们证明修复行为与界面连接，不能替代真实模型的回答质量验收或公网召回质量验收。
