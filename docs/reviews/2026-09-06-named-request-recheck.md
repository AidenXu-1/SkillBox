# 指定对象查找再次复核

本轮由用户的两张正式应用截图触发。结论：截图中的失败成立，之前“精准查找已解决”的验收范围过宽。已定位识别和任务承接缺口，当前正式版尚未修复这些缺口。

## 真实记录与复现

从当前正式应用读取两条用户搜索记录，并直接连接本次正式 Release 的核心程序文件进行本地复现，没有重新实现一套判断规则。

| 用户表达 | 实际行为 | 用户需要的行为 |
|---|---|---|
| 帮我找卡兹克写作的skill。 | 泛需求推荐，没有作者条件，混入其他作者作品 | 限定作者，再核对写作用途 |
| 帮我找卡兹克的写作skill。 | 正确识别卡兹克 | 同上；多一个“的”不应改变结果范围 |
| 我记得卡兹克有两个写作skill啊。 | 又开始一个泛需求任务 | 承接原作者，核对是否遗漏其他仓库作品 |
| 有个human writing的skill。 | 泛需求推荐，原作者条件没有保留 | 将完整名称作为查找对象，并承接当前作者 |
| human-writing | 正确进入指定名称查找 | 同上；空格和连字符形式应正确处理 |
| 我要找一个小黑配图的skill。 | 只用这句中文原话检索，零候选 | 识别公开中文叫法对应的真实 Skill；不混入相似作品 |
| 我找一下vibe-project-foundation-skill这个skill | 正确进入指定名称查找 | 保留现有行为 |

正式记录中的卡兹克三轮全部为 scenario。两次追问还生成了“上一任务的结果”，对应程序确实把它们当作新任务。小黑配图这一轮 83 次资料请求、4 次 GitHub API、1 次外部工具调用，未触发预算上限；因此不能把零候选归因于本轮请求预算耗尽。

## 已确认根因

1. 作者识别依赖固定句式。`DiscoveryRequestRouter.swift:194` 对作者后面的助词、用途以及 Skill 之间的结构有要求，用户的自然表达没有匹配，作者条件因此根本没有建立。后续查询词虽含 KKKKhazix，却只是搜索提示，不能限制最终作者。
2. 名称识别偏向带连字符或下划线的英文名称。`DiscoveryNamedSkillRequest.swift:18` 没有覆盖空格形式；另一组句式规则也没有覆盖“有个 human writing 的 skill”。结果名称被当成用途交给模型扩展。
3. 追问承接仍依赖关键词和目标文字是否相同。`DiscoveryRequestRouter.swift:214` 没有把这两次补充识别为延续；`DiscoveryModels.swift:1032` 创建了新目标，`AppModel.swift:845` 随之切断原任务上下文。
4. 中文叫法与正式身份之间没有核实过的映射。“小黑配图”确实有对应的公开作品，但当前路径既没有解析这个叫法，也没有从中文检索结果中建立对应身份。模型规划本轮又因输出截断失败，最后仅剩中文原话查询。

AI 的多次输出截断与结构校验失败是实际存在的另一层问题，但它不能解释作者条件为什么在本地就被丢掉，也不能成为依赖模型猜测指定对象的理由。

## 与最近修改的关系

- 当前正式程序 SHA-256 仍为 `0a25a9440c2ce1c6e48cede1bdc05dbf449beb240d4a83c87c5aa78d89604b39`，清理没有替换应用或改变它的内容。
- 卡兹克第一轮发生于 16:12，早于本次 17:18 完成的旧版本清理。
- 与上次盲审修复前保存的原始文件摘要比较，`DiscoveryRequestRouter.swift` 和 `DiscoveryNamedSkillRequest.swift` 内容完全一致。两个已复现的对象识别缺口在那一轮之前就存在。
- 这能证明识别缺口是此前漏验，不能据此宣称整个查询链路每个环节都没有变化；本轮没有对所有旧程序作完整行为比较。

## 受控公开查询

沿用现有生产搜索组件，人工指定查找对象，不使用模型、不读取用户密钥、不写入用户搜索记录：

- 指定 `human writing`：找到 4 份完整同名的 `human-writing`，包括 `kkkkhazix/human-writing`；没有混入 no-ai-slop 等不同名称的作品。46 次资料请求、4 次 GitHub API、0 次外部工具调用。说明空格形式可被底层匹配，错误发生在前面的对象识别。作者限制仍需正确承接，才能排除其他同名作品。
- 指定 `ian-xiaohei-illustrations`：找到包括 `helloianneo/ian-xiaohei-illustrations` 在内的 7 份同名候选。29 次资料请求、2 次 GitHub API、0 次外部工具调用。作者仓库的公开说明与“小黑正文配图”一致：[原作者仓库](https://github.com/helloianneo/ian-xiaohei-illustrations)。

这些测试验证底层可达性；手动指定对象不等于正式应用已经自动识别正确，也不等于中文别名可全部找全。测试使用每个查询最多 10 个候选，与用户实际轮次的 64 不同，不作性能提升对比。

## 修复与验收应收窄到的边界

- 完整对象身份应独立于固定句首、助词和英文分隔符；识别不确定时保留歧义，不能静默改成泛推荐。
- 作者、名称、仓库应共同限制结果；用户补充名称是在收窄当前任务，不能自动撤掉作者。
- 中文别名需要有公开来源支持的身份解析；不能仅给“小黑”塞一个特判后宣称任意中文名称都可达。
- 以用户三轮原话的最终列表作为验收，同时保留已通过的英文完整名称、真正换任务和模糊推荐反例。

本轮完成调查和受控复现，没有修改产品源码、重新安装应用、改变用户设置或调用付费模型。不将根因定位记录为修复完成，也不继续把指定对象查找列为全面通过的宣发前验收项。
