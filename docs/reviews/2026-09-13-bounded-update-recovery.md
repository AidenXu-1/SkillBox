# 更新、恢复与备份清理的限定检查与修复

用户在连续评审后要求客观区分真实风险与过度检查，并确认“先检查这条完整流程，再集中修复”。基线 `7746187`（产品 `cdc59f7` / Build 12）。本轮不扩展到发现、AI、授权、公开发行或其他产品功能。

## 收口标准

只修有源码调用路径和复现证据、影响资料安全或功能完成的问题。正常完成、中途失败、重启接续和界面反馈四类均有验证结果后收口；纯显示瑕疵不作为阻断项，不无限追加假设场景。文件被外部改变时允许停止并保留，不以强删或覆盖来满足数量限制。

## 检查矩阵

| 边界 | 结论及处理方向 |
| --- | --- |
| 更新开始记录保存失败 | 内容尚未变化；保存失败后需撤回未落盘内存状态 |
| 候选复制、校验或旧版归档失败 | 当前内容保留，沿用既有检查 |
| 中央替换后记录失败 | 取消先删当前内容再回拷的异常分支，使用已有安全交换和恢复执行器 |
| 更新内容成功、最终成功记录保存失败 | 已隔离确认当前仍是新版本却记录为已回退；与上一项统一修复 |
| 安装位置复制、交换或结束记录失败 | 复用已有整体恢复和救援记录；移除协调器重复恢复中央的路径 |
| 恢复自身失败及重启 | 未完成状态和完整内容须保留，不能进入普通过期清理；沿用现有持久恢复记录 |
| 来源版本记录与更新提交 | 纳入同一提交边界检查，防止已更新内容与来源恢复记录脱节 |
| App 备份计划保存失败 | 零删除，沿用既有保护 |
| App 备份删除一部分后失败 | 已确认无法重试；保存待删清单，允许已知项缺失并核对所有尚存内容 |
| App 备份全部删除后登记失败 | 已有删除意图加目录缺失的接续机制，继续验证 |
| 尚存备份新增、改动或变为链接 | 停止并保留；不能为重试跳过保护 |
| 替代备份损坏、旧摘要、七天及一份 | 继续已有完整性与时间边界，补跨语言接续验证 |
| 未登记创建残片 | 原件和旧套不受影响，遵守保留未完成资料的既有合同，不另造自动清理框架 |
| 恢复失败后的历史显示 | 低优先项；刷新真实状态即可，不重做界面设计 |

## 证据

- 已确认的原始故障及反证见 [Build 12 最终独立评审](2026-09-13-backup-final-review.md)。
- 本轮补充末次成功记录保存失败：`scratch/bounded-update-audit/final-save-failure.swift`，主 Agent 复跑 `primary-final-save.log`。仅一次末次写入失败，当前仍为 v2、事务却为 rolledBack，清理后旧归档消失；属于同一未核实完成状态的根因。
- App 清理限定审计未增加阻断问题；创建失败残片按既有保护保留，不能将其夸大为当前资料丢失。
- 来源记录后存已通过真实 AppModel 入口确认：一次来源记录保存失败后内容 B、来源 A、成功事务无来源恢复信息，界面仍保留预览；重启跳过，点击重试生成 B→B 并淘汰 A。探针 `scratch/bounded-flow-audit/source-journal-probe.swift`。这与最终成功记录失败归入同一更新提交根因，统一修复，不另加恢复框架。

检查已结束，修复清单冻结为更新提交/失败恢复一致性、App 部分删除接续两组。历史状态刷新属于同一失败出口的局部处理。Spec v2.60 已记录实施边界。

## 实施结果

- `LibraryStore` 中央更新使用现有安全目录交换，保存失败直接交换回旧内容；回换本身失败时保留完整目录和旧归档并报错，不再先删除当前内容再回拷。记录、安装关系及来源恢复保存失败时撤回未落盘内存状态。
- 两个更新入口共用协调流程，变更前保存来源恢复信息，来源写入与部署均完成后才提交成功；失败统一进入已有恢复执行器，不重复单独恢复中央内容。AppModel 普通更新及旧包整理入口统一接入，失败后刷新真实状态。
- App 清理用同格式 `removalInventory` 保存条目的路径、类型、权限、摘要或链接目标，待清理记录采用 v3，普通备份仍为 v2。已知条目缺失可重试，尚存条目和新增内容仍需核对；目录描述符与不跟随链接的打开方式防止删除落到备份外，登记标记最后删除。
- 不改一份/七天及启动/手动检查规则，不启动小时任务；创建失败残片无法清除时明确位置，保持未登记内容保护。
