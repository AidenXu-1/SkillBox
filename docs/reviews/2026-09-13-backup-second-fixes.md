# 第二轮备份与恢复问题修复

用户要求先确认问题成立，再修复。对应 [第二轮独立评审](2026-09-13-backup-second-review.md) 的六项问题，合同为 Spec v2.59。

## 成立性与根因

六项均经复核成立。第 1、3 项依赖恢复来源缺失、损坏、外部修改或写入失败；第 4 项依赖删除已经完成而登记写入失败；第 5 项依赖备份权限被改动；第 6 项依赖清理失败。它们不代表正常每次操作都会出错。

其中，登记重试问题由前轮新增保护与旧保存顺序组合引入；其余为此前测试未覆盖的既有恢复流程。第 2 项还使用真实 ContentView 的隔离 App 确认：仅中央更新的记录显示可恢复，但确认窗为“0 个位置”且按钮禁用。没有凭评审文字直接把猜测当成缺陷。

## 修复内容

| 问题 | 处理 |
| --- | --- |
| 启动恢复使用缺失/损坏来源 | 改动前核对全部需要的恢复来源，已经处于操作前版本的目标保持原样；恢复内容先复制核对，再替换 |
| 中央更新确认按钮禁用 | 确认窗单独列出“我的 Skills”保存版本，可取消、确认；过期或已恢复的记录仍不能确认 |
| 组合撤销部分完成 | 提前检查中央实际内容；整轮恢复使用持久救援记录，失败补偿已经改变的位置和中央状态；清理失败与恢复结果分开 |
| 删除后登记失败卡重试 | 先保存整批清理意图，再从旧到新删除；下次接续已登记但未收口的清理，仍核验尚存内容与替代备份 |
| 权限/类型漏检 | 新摘要同时保存内容、类型和权限；特殊文件拒绝；旧 App 迁移核对当前用户的实际执行资格 |
| 清理失败仍显示旧入口 | 失败出口重新读取已持久化的恢复状态，关闭已经失效的操作入口 |

同时同步 Spec 中仍写“至少 30 天、10 个事务”的旧条款，统一为一份上一版、7 天，启动或手动检查。内部救援记录不出现在用户操作列表，也不能作为用户可点的恢复入口；完成且清理成功后移除内部登记。

## 验证方法与边界

- 先把已确认的问题写成失败测试，再修根因。界面清理状态在 `scratch/backup-repair2-presentation-red.log` 有两个失败断言；核心恢复及后续补偿的失败结果见 `scratch/review2-retention/red.log`、`compensation-red.log`；App 清理及权限失败结果见 `scratch/review2-app-backups/fix-python-red.log` 和 `permission-owner-*-red.log`。
- 独立复审指出两个初版修复缺口，已纳入本轮：单目标安全不足以保证整轮恢复失败后一致；任意执行位存在不足以证明当前用户能运行旧 App（0655 情况）。因此没有用初次专项通过直接收口。
- 旧备份摘要继续兼容，v2 前缀让旧实现停止删除而不会忽略新增信息。旧登记没有保存任意文件的历史权限，迁移只能在内容与已知 App 启动资格核对后建立当前权限基线，不宣称还原了缺失的历史权限。
- 真实 Build 10 备份的隔离副本验证：到期前一秒移除 0 份，到期移除 1 份，重复移除 0 份；旧摘要、新摘要的原生/Python 结果一致，创建与到期时间未延长，真实备份内容不变。证据 `scratch/backup-repair2-real-compat.json`。
- 首次修复版隔离 UI 已完成按钮、取消和恢复内容验证，但使用尚未创建的 `/private/tmp` 别名路径触发维护位置保护，不能记为全通过；后续 QA 改用仓库 scratch 独立目录并先创建再标准化，没有放宽产品保护。
- 所有故障注入和恢复操作使用隔离资料。持久保存验证针对进程中断与写入错误，不宣称跨卷操作是瞬时原子提交，也没有做断电或硬件故障实验。
