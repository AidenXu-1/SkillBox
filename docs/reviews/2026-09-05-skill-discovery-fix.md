## GitHub 限制的现场证据

官方 `/rate_limit` 返回 `core.limit=60`、`core.used=60`、`core.remaining=0`，恢复时间为北京时间 11:50:49；普通搜索分钟额度为 `search.limit=10`、`search.remaining=10`。说明本次耗尽的是读取仓库资料等普通 API 的匿名额度，不能笼统归为搜索关键词问题。

GitHub 匿名额度按出口 IP 共享，无法从这一张快照确定 60 次请求分别来自本应用、其他程序还是同一出口的其他使用者。旧的精确仓库路径会扩大到多来源搜索和资料核验，确实增加不必要的调用；测试过程也会消耗额度。没有使用代理轮换、额外账户或其他规避限制的方式。

依据：[GitHub 额度说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[GitHub 搜索限制](https://docs.github.com/en/rest/search/search)。搜索代码接口另需身份认证，不可假设匿名 code search 可用；这条广域搜索能力未在本切片重构。

## 后续追查：调用量与既定策略不一致

用户追问“一分钟为什么触发这么多次”后，进一步核对当前组合方式。60/60 快照是出口 IP 在小时额度窗口内的累计用量，不能证明本应用在一分钟内发出了 60 次请求；此前没有逐请求现场日志，无法还原这 60 次的时间及归属。

代码确认三处缺口，上一轮的完整地址修复没有覆盖它们：

1. `AppModel.swift:265–285` 为媒体线索再建立独立的 GitHub、skills.sh 和目录对象；与普通搜索各自缓存已核验结果。最后合并候选只能消除重复显示，无法收回已发出的重复请求。
2. `SkillsShDiscoveryProvider.swift:332–333` 先补仓库资料，再核验公开正文。因此即使正文能够直接读到，每个新的仓库仍先消耗一次 API 请求；正文路径找不到时还会查树和内容。12/12/8 是每个对象、每次调用的候选核验上限，6 是模型比较的候选数，都不等于整个用户操作的 GitHub 请求预算。
3. 媒体名称解析器把目录、skills.sh、GitHub 放进并发协调器，未实现 ADR-0019 第 5 条所写的逐层兜底顺序。共用的额度门只在响应告知额度为零或被限流后停止后续请求，没有整个用户操作的事前请求预算，也没有为后续加入保留额度；已发出的并发请求不会因此撤回。

使用真实 `SkillsShDiscoveryProvider` 与 `DiscoverySearchCoordinator` 代码执行完全离线的 URLProtocol 计数，固定 12 个相同候选、全部公开正文一次读成功：

| 条件 | 已核验候选 | 全部请求 | GitHub API 请求 | 不重复的 GitHub API 地址 |
| --- | --- | --- | --- | --- |
| 一个新来源对象 | 12 | 37 | 12 | 12 |
| 同一个对象再次查找 | 12 | 1 | 0 | 0 |
| 两个新对象并行、共用额度门 | 12 | 74 | 24 | 12 |

这里 74 次包含 skills.sh 和 raw 正文读取，不能全部算作 GitHub API 额度。该实验验证组合方式确实会重复请求，不是对现场 60 次调用的重放。计数脚本与输出位于 `scratch/discovery-outcome-fix/RequestCountProbe.swift`、`request-count-result.txt`，未访问真实网络、凭据、资料库或 Agent 目录。

后续修复应以一次用户操作为单位共享已核验结果和请求预算，媒体名称按约定逐层兜底，优先使用直接正文证据；仓库资料按实际需要补充，加入所需的来源、版本和安全核验继续保留。验收必须核对最终组合链路的请求总数及重复数，不能仅用单来源测试通过推导整体符合策略。本次追查只记录诊断，没有改动正式产品代码或重新替换候选应用。

日志和隔离入口保存在 `scratch/discovery-outcome-fix/` 及临时验收目录；完整测试与构建日志分别为临时目录中的 `skillbox-outcome-final-all-tests.log`、`skillbox-outcome-release.log`。
