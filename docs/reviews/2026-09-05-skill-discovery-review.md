## 1. P1：已知仓库地址会漏掉真实存在的 Skill

真实复现：新建寻找，输入 `https://github.com/op7418/Humanizer-zh`。10:32:28 开始，10:33:09 返回 0 个推荐，耗时 41 秒。随后新建寻找，输入 `Humanizer-zh Skill`，10:35:30 开始，10:35:38 返回 9 个同名候选，耗时 8 秒，其中包含同一个 `op7418/humanizer-zh`。两轮都处在 GitHub 限流期间，第二轮仍通过公开正文直读找到了目标。

仓库与根目录说明文件本轮亦经公开网页核实：[作者仓库](https://github.com/op7418/Humanizer-zh)、[SKILL.md](https://github.com/op7418/Humanizer-zh/blob/main/SKILL.md)。

原因定位：`DiscoveryRequestRouter.swift:111–115` 把根目录 `SKILL.md` 路径转换为 nil；`RoutedSkillDiscoveryProvider.swift:58–70` 只在非 nil 路径时调用直接读取，否则把已知地址转成 `repo:owner/repo` 发给多个普通搜索来源。普通 GitHub 路径进一步走 code search。复现程序确认，即使用户提供完整的 `/blob/main/SKILL.md`，也只触发 `generic_search=repo:op7418/Humanizer-zh`，没有触发直接读取。

影响：用户给的信息更准确，反而更慢或找不到；当公开 API 受限时尤其明显。

修复方向：保留“明确指向根目录 SKILL.md”的事实；已知仓库先定向核验，允许使用已有的公开 raw 读取能力，再对缺少路径的多 Skill 仓库做必要发现。不要让明确路径依赖通用搜索结果排名或搜索额度。

## 2. P1：免费兜底流程会忘记用户前一轮目标

本地确定性复现：上一轮是“帮我找能做公众号排版的 Skill”，分别补充“最好支持中文”“不要收费”“只要能离线用的”。当前 fallback 都把这句补充直接替换为新 goal，查询只剩补充句，约束数组为空。原来的公众号排版任务消失。

位置：`DiscoveryModels.swift:855–875`。只有固定的“质量不高、继续深挖”等反馈会保存上一轮目标，其余常见补充没有合并进旧需求。

影响条件：没有配置 AI，或 AI 规划失败、超时、输出无效而回退到本地流程时。不是宣称每次 AI 正常返回时都失败。当前产品明确承诺可继续补充条件且 AI 失败仍可用，因此这条失败分支必须独立成立。

修复方向：识别补充条件与换任务，补充时保留旧 goal，把中文、费用、离线等条件加入约束；增加无 AI 和 AI 失败时的多轮用例。

## 3. P2：PPT/Excel 被当成 GitHub 仓库

真实窗口输入“帮我找一个 PPT/Excel 的 Skill”。保存记录显示 route 为 `exact`、查询为 `repo:PPT/Excel`，完全偏离了找办公能力的意图。随后主动停止本轮，未等待其空结果。只读复现程序得到相同分类。

位置：`DiscoveryRequestRouter.swift:120–126`。正则在整句里看到任意满足形式的 `英文/英文` 就提前判断为仓库，阻止后续任务理解。

影响：普通用户用斜杠并列工具名，搜索却跳过语义理解，也不会补充 PPT、表格能力关键词。

修复方向：裸 `owner/repo` 应有明确的仓库上下文或完整输入形态；自然语句里的工具并列不能直接当 GitHub 身份。

## 4. P2：未完成核验却把主结果写成“没有找到”

第一轮仓库查询的记录为 `partiallyCompleted`，有 4 个核验失败、99 个待核验候选及 GitHub 限流信息。但默认首页显示“没有找到完全匹配的 Skill”；必须主动展开“查看本轮覆盖情况”才看得到限流以及 10:50 后重试的信息。

位置：`RoutedSkillDiscoveryProvider.swift:72–78` 只凭候选数为 0 生成 `exactNotFound`，`DiscoveryModels.swift:561–566` 再优先使用该结论，没有区分“核验完整而不存在”和“目前无法核验”。

影响：用户会以为 Skill 不存在，可能修改正确地址或放弃。此次真实场景证明目标存在，而且另一条查找方式能够读到。

修复方向：没有任何推荐且查询/核验受阻时，主结果应直接说“暂时无法完成核验”，显示可重试时间；详细运行数字仍可折叠。已有有效推荐时继续保留结果优先。

## 5. 体验缺口：找到以后仍缺少“怎么用”的说明

真实检查新查找中的 `ai-zixun/humanizer-zh` 和 `op7418/humanizer-zh`：右侧只有作用、热度及加入按钮。第一项作用基本为英文长段落；没有单独的使用步骤和启动提示词。空状态却承诺会展示用途、适用场景和使用方式。

原因：`AppModel.swift:1111` 当前主动清空候选 usageGuide；`ContentView.swift:1215–1220` 没有 guide 时只把原始摘要放入 purpose，其他区域按空值隐藏。此前为防止候选影响模型自由文案而收紧边界是明确设计，不应为了填满卡片重新放开不受约束的模型生成。

建议：保留边界，用可核验作者资料提供简短中文说明和使用入口；确实缺少步骤时直接注明，并提供读取原始说明的明确入口。此项归类为体验缺口，不与前四项确定的逻辑错误混淆。
