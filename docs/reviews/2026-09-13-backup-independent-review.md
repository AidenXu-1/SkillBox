## 优先修复

### 1. P1：旧恢复失败记录会淘汰后续成功更新的唯一上一版

位置：`app/Sources/SkillBoxCore/BackupRetention.swift:24-27`，淘汰判定在第 38-45 行，实际删除在 `LibraryStore.swift:204-210`。

失败记录先占据同一 Skill/安装位置的备份名额，不考虑它是否早于后来的成功操作。真实生产调用链的隔离复现：安装 A → 更新 B 时外部编辑导致恢复失败 → 中央保存 C 成功 → 保存 D 成功。C/D 事务均立即标记备份过期；D 对应的上一版 C 归档被实际删除，撤销 D 被拒绝。当前内容 D 仍存在，问题是失去上一版恢复能力。启动恢复只重试运行中事务，旧失败记录不会自动退场。

应保留失败救援资料，同时独立保留后来成功更新的上一份，不让历史失败永久占据普通备份名额。证据：`scratch/backup-review-20260913/retention-repro.swift`、`retention-repro-output.txt`，编译复现命令见同目录 `retention-findings.md`。

### 2. P1：原生与 Python 摘要排序不一致，当前真实 App 备份到期将无法清理

位置：`app/Sources/SkillBoxCore/AppRollbackBackups.swift:117`，对照 `app/Scripts/rollback-backups.py:58`。

Python 按路径组件排序，原生按完整相对路径的字节排序。文件夹 `a/` 与文件 `a.txt` 并存就会得到不同摘要。内容未改过，原生清理却报“应用回退备份已被改动”，保留到期文件。

当前唯一有效的 Build 9 回退资料已只读核对：登记值与 Python 都为 `3985b9b4…240ca49b`，原生为 `da5155fd…263145ba`，主 Agent 再算一次得到相同差异。真实内容仍符合登记；没有对真实备份执行清理。初次界面验收处于未到期状态，因此直接跳过了摘要检查，无法发现此问题。

需要兼容已有登记的排序规则，不能仅改新备份的算法。证据：`scratch/backup-review-20260913/real-backup-digest.json`、`results.json` 的 `digest_path_order`。

### 3. P1：最新备份已损坏或消失，仍会删除旧的完整备份

位置：`AppRollbackBackups.swift:51-52` 与 `rollback-backups.py:108-111`。

存在两份同组登记（例如新备份登记后进程中断，尚未淘汰旧备份）时，清理先认可最新登记的名额；最新备份未到期就完全跳过检查。即使它已经损坏或目录消失，仍把旧完整备份删除。两端各复现“最新被改动”和“最新丢失”，旧完整备份都被删除；丢失样例最终两份都不存在，原生仍返回成功清理一份。

清理被替代的备份前，应确认用于替代它的最新一份仍完整可用。证据：同目录 `results.json` 的四个 `newest_changed` / `newest_missing` 样例。

## 其他问题

### 4. P2：合法时区混用时，Python 会误删较新备份

位置：`rollback-backups.py:103-104`。

登记支持带时区的原创建时间，但清理按原字符串排序。较旧 `20:00+08:00` 与较新 `15:00+00:00` 同日登记，脚本错误地保留前者、删除后者。原生按真实时间排序，无此问题。子 Agent 实际删除隔离样例，主 Agent 独立只读预览也得到相同错误。应统一按解析后的绝对时间排序。

证据：`results.json` 的 `timezone_order`，以及主 Agent 的 `timezone-sort.json`。

### 5. P2：首次创建遇到旧备份清理失败，应用识别入口没有写入

位置：`rollback-backups.py:155-159`，对照 `AppRollbackBackups.swift:23`。

脚本先清理旧备份，再写应用所需的登记位置。首次建立此入口时，旧备份被改动导致清理抛错：新备份已完整登记，两份目录都在，但配置没有生成。后续启动和手动检查直接返回零，可能显示“没有需要清理的备份”。已有正确配置时不受此问题影响。

应在登记完成后可靠保存发现入口，清理失败不能让已登记资料从原生维护入口消失。隔离复现：`flow-config-repro.py`、`flow-config-result.json`，输出为 `create_exit=1`、`live_entries=2`、`native_location_exists=false`。

### 6. P2：启动检查遇到用户正在操作，会放弃这次检查且不补跑

位置：`AppModel.swift:1519-1522`；唯一启动调用位于第 442 行。

启动第 435 行已展示资料，其后经过多次异步等待才检查备份。用户期间进入导入/恢复预览或其他忙碌操作，检查直接返回。忙碌结束后没有补检。该问题只影响此次启动的自动维护，用户手动检查或下次启动仍可补救。

依据为调用链及现有 `manualCheckFeedback` 测试：测试通过第二次主动调用才能完成检查，并没有验证自动延后执行。此次未用真实前台时序复现。建议保存待检查状态，在阻塞操作结束后完成本次启动检查，不恢复每小时循环。

### 7. P2：成功操作后的清理错误被丢弃，取消定时任务后也没有周期重试

位置：`LibraryStore.swift:909-912`。

成功更新/撤销后执行清理使用 `try?`。如果旧备份因权限或路径问题不能清理，失败不会传给设置检查结果或通知。保留的注释仍声称周期维护会重试，但周期循环已经移除。数量上限可能暂时失守且用户不知情；下一次启动或手动检查仍会重试。这个问题不意味着当前 Skill 内容被破坏。

由异常吞掉路径静态确认，本次未另做权限故障注入。应让成功写入保持成功，同时单独记录并展示备份维护未完成。
