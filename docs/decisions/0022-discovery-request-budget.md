# ADR-0022：按一次寻找共享请求并控制 GitHub 用量

- **状态**：已采纳
- **日期**：2026-09-05
- **范围**：落实 ADR-0019 的媒体名称逐层兜底，并补齐整个用户操作的请求预算；不改变三栏布局、推荐品质门槛或加入时的安全核验。

## 原因

普通发现与媒体名称定位拥有不同来源对象，各自缓存无法阻止同一轮重复读取。同样 12 个候选的离线实测产生 74 次请求，其中 24 次为 GitHub API，只有 12 个不重复 API 地址。skills.sh 还在公开正文可读时提前查询仓库资料。候选数量上限不能限制实际请求数量，响应后才处理限流也无法阻止已经发出的请求。

## 决定

1. 最外层寻找创建共享请求上下文，普通来源和嵌套媒体定位均继承它。以地址、身份、响应格式和大小限制识别相同读取，共享进行中的任务及已完成响应。结束或取消后关闭上下文、清除正文并取消剩余任务，后续寻找使用新上下文。
2. 每轮 GitHub API 上限 12 次，自动跳转也先取得预算。匿名已知剩余额度不高于 12 次时停止发现请求，本应用进程内另设滚动一小时 36 次匿名发现上限。其他应用共享出口额度，因此不能保证加入时一定还有额度。
3. 媒体名称依次由可信目录、skills.sh、GitHub 定位；只有未解析的名称进入下一层，某一层失败仍继续兜底。普通多来源发现保留既有并行召回，社区证据仍必须绑定真实 Skill。
4. 优先读取公开 SKILL.md，失败时才补充定位所需仓库资料；不会为了显示 Star 先消耗 API。无登录身份时跳过必须认证的代码搜索。
5. 覆盖详情保存候选资料请求、GitHub API、复用及预算阻止次数。预算停止与 GitHub 服务端限流分别说明，保留已核验结果；计数不包含媒体工具自身的所有网络请求。取消或抛错的运行不保证含最终计数。

## 成本与限制

- 共享响应仅存本轮内存，完成响应保留上限 128 项、8 MiB，进行中的响应仍分别受原有正文大小限制。无新增磁盘正文缓存、数据库、依赖或付费搜索。
- 运行记录新增四个整数，历史缺失字段兼容，继续受原有 64 MiB 累计记录上限约束。
- 本地匿名滚动计数不跨应用重启保存；GitHub 返回的限制仍生效。不同地址或身份不强行合并。
- 公开正文成功时仓库 Star 可能未知，界面沿用“暂无公开数据”。加入时继续核对真实仓库版本及安全信息。

## 验证

`DiscoveryRequestPolicyTests` 覆盖实际应用组合、同轮复用、并发预算、跳转预算、匿名余量、逐层兜底与失败恢复、取消及下一轮、旧记录兼容和提示口径。固定相同 12 个候选的双来源实验由 74 次降为 25 次，GitHub API 从 24 次降为 0，正文读取从 24 次降为 12；这是离线固定样本结果，不能当成所有真实搜索的固定调用量。

完整回归、构建和真实窗口验收分别记录于 `docs/reviews/2026-09-05-skill-discovery-fix.md`。自动化通过不代替真实用户出口验收。
