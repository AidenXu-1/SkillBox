# ADR-0021：发现页先交付结果，并统一强推荐与热度口径

- **状态**：已采纳
- **日期**：2026-09-05
- **修正范围**：发现页最终回复、推荐准入数量和热度指标展示。

## 背景

真实搜索已经能找回候选，但用户仍看到大段“模型截断、来源未完成、候选待核验”等内部诊断。它们占据最终回复位置，让已经有结果的一轮看起来像失败。与此同时，中栏没有显示推荐总数，固定高度的窗口经常只露出约五项，形成“系统每次硬凑五个”的错觉。右侧又按数据是否存在选择性显示安装量或 Star，导致两个不同层级的指标看起来像可以互换。

更深一层的问题是旧精品门槛允许“近期维护且说明完整”的新项目直接进入推荐。维护与文档能证明项目可读，却不能证明它已经得到真实用户认可，因此会把几十次使用量、没有独立推荐者的候选和真正热门候选并列。

## 决定

1. 有推荐时，左栏第一结论固定为“找到 N 个值得优先看的 Skill”，并说明它们已经通过真实 `SKILL.md`、用途与公开质量依据核对。
2. 模型截断、来源超时、查询触顶、待核验数量与未绑定社区线索继续保留，但只进入默认折叠的“查看本轮覆盖情况”。它们不再作为大段最终回复，也不再重复写入消息与运行记录两处。
3. 场景推荐的公开质量依据只接受三类：作者官方来源、至少 500 次 Skill 级安装量、至少两位可区分的社区推荐者。近期维护与操作说明只帮助排序和可用性判断。
4. 推荐数量没有目标、下限或上限。所有通过门槛的候选都保留；中栏标题直接显示“推荐 N 个”，零个时也不使用水货填充。
5. 详情始终同时展示“Skill 使用量”和“GitHub 仓库热度”。前者属于单个 Skill，后者属于整个仓库；缺失数据写“暂无公开数据”，零值保持为零，仓库 Star 不参与场景推荐准入。
6. 用户明确点名的 Skill 继续走精确查找，只要名称匹配、真实可读、可下载且没有阻止事实，就不受热门门槛影响。

## 成本、Token 与存储

- 不新增付费搜索、数据库、索引或外部服务。
- 更严格的公开质量门槛会减少进入模型比较的低口碑候选，从而降低无效上下文和模型 Token，而不会增加调用次数。
- 结果文案和热度展示从既有字段即时计算，不新增寻找记录字段。取消重复保存诊断后，新记录通常会略微变小；原有 64 MiB 总上限不变。

## 回退

该调整不迁移或删除旧记录。回退应用包即可恢复旧展示；旧记录里的大段诊断仍能被新版读取，但会默认折叠，不影响候选、Skill 库或 Agent 安装关系。
