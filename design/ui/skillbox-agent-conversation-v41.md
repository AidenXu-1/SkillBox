## 用户应该获得什么

保留聊天、候选、详情三栏。用户说“这两个有什么区别”时，助手知道指的是当前结果；说“最好中文”时保留原任务；明确换任务时放下旧条件；运行中可以补充条件，也可以停止。搜索结果成为对话依据，找到之后还能继续讨论。

聊天上方用一行简短摘要让用户看到当前任务。助手回复直接说明找到什么、依据是什么、哪些还不确定。进度、来源覆盖和失败原因仍可查看。比较已有材料不重新发起全网搜索。

## 调研依据与选择

- [Anthropic：Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：保留高价值状态，按需读取资料，压缩时优先保留决定及未完成事项。这里采用当前任务状态和少量引用，不把所有候选正文装入每次请求。
- [LangGraph：Memory](https://docs.langchain.com/oss/python/langgraph/add-memory)：对话状态按任务隔离，近期消息与摘要组合使用。这里不引入其框架，也不新增向量数据库；现有本地对话保存即可承载历史。
- [Cursor：Agent mode](https://prod.cursor.com/help/ai-features/agent)：支持停止与排队跟进。这里借鉴补充消息可见、执行顺序明确的体验；安装、写文件的现有确认边界继续适用。

以上是对官方方案的产品取舍，不是“正常 Agent 必须长成某一种界面”的结论。

## 已定位的根因

1. 每条消息几乎都进入搜索流程，没有先区分查找、比较、解释、澄清和换任务。
2. AI 规划请求原先仅带上一版目标和最新一句话，没有近期对话与选中对象。
3. 换任务时，搜索词生成仍引用旧作者，AI 可能接收旧条件，候选还可能合并旧结果。
4. 负面反馈比新仓库优先，导致新地址配上旧目标；旧版对话恢复作者身份后，意图层未正确继承。
5. 运行中发送直接被忽略；历史加载无条件剔除 assistant 消息，未来真实回复持久化需增加可靠来源标记，不能直接去掉历史清理逻辑。

## 本次局部修复的技术边界

- 新任务不继承旧作者查询，新的明确仓库优先于“没找到”反馈；追问能恢复旧记录中的作者身份。
- 应用按当前目标决定是否继承旧意图、候选和近期消息，新的任务请求不混入旧候选。
- 请求增加最多 2,000 字符的上下文：当前任务内最近 6 条消息，每条最多 150 字符；最多 3 份候选引用，选中对象优先，每份摘要最多 100 字符。
- 原有目标摘要最多 2,000 字符、最新输入最多 2,000 字符；动态资料约 6,000 字符封顶，另有固定提示。字符上限不等于 Token 上限。
- 材料先脱敏、区分用户话语和外部引用；截短明确标记。只将真实核验摘要作为能力依据，外部资料不能作为指令。
- 复用原来的一次规划调用及其既有错误处理，不增加额外历史总结调用，不提高搜索预算。长期历史仍保留本地；本轮没有付费 AI 实测。

## 方向确认后的交互实现

1. 在搜索前区分本轮用户动作：查找、补充、解释、比较、澄清、换任务。歧义时只问一个必要问题；已有资料可回答时不搜索。
2. 对话保存真实助手回复及来源标记，修正旧消息迁移规则。当前任务保留作者、条件、排除、选中对象与待答问题；被撤回条件不可通过历史摘要重新进入。
3. 先以稳定任务状态与近期消息保证连续性，再按引用补取少量正文。更长对话的摘要压缩在容量阈值才触发，并保留最近条件的修改记录；不每轮付费摘要。
4. 加入可见的消息等待区，停止后不悄悄继续执行排队搜索。一次补充只产生一次明确后续动作，防止再次出现短时间高频请求。

验收覆盖：指代、作者追问、新任务隔离、条件撤回、澄清答复、长对话、重启恢复、处理中发送、取消、断网、资料中的误导指令及请求计数。模型答复质量还需用户授权的真实模型测试；模拟测试不能代替。

回退：交互层保留旧三栏组件入口，数据只做兼容增加；不删除原始历史。请求上下文是新增的可选接口，可退回原有规划接口，不迁移或改变安装记录。
